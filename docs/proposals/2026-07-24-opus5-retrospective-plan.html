Opus 5 内容项目复盘与迭代方案

目标不是把流程变得更长，而是把路由、证据、素材、叙事形式和发布校验变成可验证的工作契约：先得到更可靠、更像编辑写的文章，再让 Baoyu 在正确的节点发挥作用。

结论先行

01

问题不是“少调用一次 Baoyu”

Baoyu 被放在写完后的可选动作里，导致它介入过晚；但把它改成“每次自动生图”同样是错误解。正确动作是：开题就做 Baoyu 能力预检与素材路线规划，生成/上传留到证据和版式都通过后。

02

质量瓶颈在“证据—表达”之间

当前流程会搜资料、会写、会降套话，却没有强制维护“哪条事实由什么来源支撑、该用什么真实素材表现、读者最终要拿走什么判断”。这会自然滑向官方稿摘要 + AI 补图。

03

“像人”不等于更口语

人味来自取舍、视角、证据边界、节奏和不对称的判断。把句子改短、删几个套话，只能降低模板感；它无法凭空产生作者立场，也不该伪造“我实测过”。

推荐原则：早路由，晚执行；先证据，后视觉；先观点，后润色；先草稿校验，后发布。这样既不会空耗图像成本，也不会在临近发布时才发现 GIF、外链、封面/正文角色等约束。

这次流程与仓库的已核实问题

以下把本次 Opus 5 产出中的现象，与当前工作树中的规则/文件逐项对应。前四项是工作流问题；后两项是仓库一致性问题。

观察根因造成的后果方案方向
路由过晚
写公众号文章时，Baoyu 没有在启动阶段进入生产规划。		 现有 baoyu-integration.md 明确写着“普通写作任务不自动触发 Baoyu”；而素材、封面、排版、发布均被定义为后续可选动作。 素材策略、Hero、封面、GIF、公众号支持能力在后段才逐步暴露，产生多轮返工。 在 Step 0 增加“渠道与资产预检”，先建立素材路线，但不自动生图。
素材先后颠倒
先用 AI 制作案例说明图，后发现官方动画/页面可用。		 研究步骤只要求多渠道搜索并保存 knowledge.md，没有第一方素材优先级、资产清单或“官方/编辑生成”标记。 容易出现“用编辑图解释官方案例”的误读，也会让正文看起来像空泛的 AI 拼贴。 把“素材搜索”变成与事实搜索并列的强制产物：sources.yaml + asset-manifest.yaml。
人味判断失焦
现有“降 AI 味”主要落在禁词、短句、口语化。		 三遍审校和 CLI 更擅长检查表面统计特征；没有作者立场、信息取舍、反例、真实性边界等编辑门槛。 可能从“规整的 AI 文”变成“刻意口语的 AI 文”，仍缺少值得读者转述的判断。 用“编辑意图 + 论证链 + 真实细节”替代“AI 味百分比”作为主判据。
表现形式后置
封面、Hero、案例图的角色边界是在制作中才被澄清，且出现素材复用。		 没有文章 storyboard 与素材角色矩阵；视觉步骤发生在最终稿完成之后。 Hero 可能重复封面，案例图可能只承担装饰而不提供证据，移动端阅读节奏变弱。 在大纲阶段锁定每个视觉位的任务，明确“允许省略 Hero”。
Skill / 文档漂移 主 Skill 引用了 workflow.md、title-guide.md、principles.md、checkpoint.md，但当前工作树中不存在；README 还链接了多份未跟踪文档，并列出了未落地的模块。 Agent 可能遵循不存在的引用，用户也会对已承诺能力形成错误预期。 先做“文档与运行规则一致性”修复；新增 CI 检查引用路径。
公开仓库基础 当前工作树与可达 Git 历史的简单密钥模式扫描未发现命中；.gitignore 已忽略 .writing-master/。 基础是好的，但新的发布、素材、MCP 配置会带来新的泄露面。 把密钥、浏览器 profile、发布草稿、素材 URL、运行记录全部明确为仓库外状态；提交前设自动扫描。

说明：最后一项是有限规则扫描，不等同于完整安全审计；它只能说明本次检查没有发现常见 key-shaped 字符串。

这次项目应该吸取的四条具体教训

1. “官方案例”首先是证据，不是插画主题

当官方已经给出 demo、视频、GIF、截图、基准图或开源仓库时，优先把它当作原始材料。编辑自制图可以存在，但它的职责必须是解释，而非伪装成“官方案例画面”。

  • 原始素材：标记 official / primary；
  • 编辑解释图：标记 editorial，不使用官方口吻；
  • 纯装饰图：若不能推动理解，直接删除。

2. 微信文章的形式必须从第一屏开始设计

封面是点击前包装；Hero 是读者进入正文后的第一份证据或情绪；案例图承担验证；信息图承担压缩。它们不是同一张图的不同尺寸，也不必每篇都有 Hero。

  • 封面与 Hero 默认不复用；
  • 每张图填写“读者看完多知道了什么”；
  • GIF 先验证平台上传方式，再写入正文结构。

3. 新模型发布文章要有“读者决策”，不是发布稿转述

Opus 5 类文章最有价值的形式不是“指标罗列”，而是：这些证据足以让哪类读者把它放进测试名单，哪类读者暂时不该换。 这会逼迫作者选择主线，也会让 Benchmark、案例和价格为同一个判断服务。

4. 工具层适合做确定性检查，不适合伪造品味指标

禁词、外链、图片路径、GIF、素材重复、来源缺失、秘密扫描都能自动检查；“是否像人”“有没有洞见”要改成带证据的编辑 rubric，由人/模型评审，而非输出一个看似精确的 AI 味百分比。

建议的 Writing Master v2 工作流

保留现有“从 brief 到发布”的骨架，替换其中几个过于宽泛的步骤。每一步都有明确文件产物和通过条件。

Step 0

内容契约与能力路由

输入：主题、平台、时效、是否需要发布。
新增判断：内容类型（发布快讯 / 深度分析 / 实测 / 观点）、证据等级、素材政策、来源展示策略、是否允许 AI 解释图。
Baoyu：只做 capability preflight：确认可用的配图、封面、HTML、公众号、X 能力与平台限制，不生成任何图。

channel_contract:
  platform: wechat
  article_mode: launch_analysis
  visual_mode: evidence_first
  source_display: none | appendix | inline
  ai_visuals: editorial_only
  publish_intent: draft_only
Step 1

双轨调研：事实与素材同时搜

事实轨：官方发布、API 文档、benchmark 说明、独立测试；每条可写入正文的主张要有来源、时间、证据级别和表述边界。
素材轨：第一方 GIF / 视频 / 截图 / 图表 → 一手技术资料 → 独立媒体 → 编辑图。先找现有真实素材，再决定是否需要制作解释图。

产物：sources.yaml、claims.yaml、asset-manifest.yaml。

Step 2

角度、读者决策与 storyboard

不只列 3–4 个标题，而是确定一个“读者看完应该做什么”的判断句；再把正文拆成阅读节奏和视觉节奏。没有证据价值的 Hero 直接不设。

editorial_brief:
  thesis: "不是谁的绝对分更高，而是谁更值得放进日常任务测试。"
  reader_decision: "哪些团队现在该试，哪些先观望。"
  counterweight: "官方数据不能替代独立复现。"
  human_voice: "克制、判断优先、不过度代入个人实测。"
Step 3

写作：证据链服务于一个编辑判断

每个段落必须回答：它帮助读者作出哪个判断？其中事实、官方说法、编辑推断分别是什么？禁止把未做的实测写成第一人称体验。

Step 4

三层审校，而非三次泛改

证据审校：事实、时间、来源、推断边界。
编辑审校：主线、取舍、反例、读者结论、是否能删去 20% 仍更强。
表达审校：节奏、重复、语言自然度、伪人设与模板句。

Step 5

Baoyu 视觉生产与公众号构建

仅在 asset manifest 审核通过后执行：官方素材下载/转码/上传、必要的编辑信息图、封面、HTML。每一项保留来源或生成提示词，并在正文中准确标注身份。

Step 6

移动端验收与发布闸门

生成 mobile preview；检测图片路径、GIF 数量、重复素材、锚点、外链策略、封面角色、草稿更新结果。只有明确的 PUBLISH 指令触发公开发布；“继续”只推进下一份可审阅产物。

新的质量门槛：把“像人”拆成可审的东西

内容与证据门槛

  • 每个关键数字、产品能力、客户案例有 claim_id 与来源；
  • “官方说法”“独立验证”“编辑推断”三个层级不混写；
  • 有一个真正影响结论的反例或限制条件；
  • 每节都能写出“读者因此该如何判断”。

人味 / 编辑性门槛

  • 有明确主张，而非平均分配所有信息；
  • 开头给出张力或问题，不以产品百科开场；
  • 不虚构“我用了一周”“我实测”等个人经验；
  • 删掉任何换一个产品名也成立的句子；
  • 允许句长、段落长度和信息密度不对称，但不故意装口语。

视觉与形式门槛

  • 封面、Hero、案例、图表各有唯一职责；
  • 无“同一素材同时当 Hero 和案例证明”的复用；
  • 官方 GIF / 视频优先，编辑图只解释不冒充原始素材；
  • 移动端 390px 预览时文字、裁切和图表可读；
  • 图片在公众号草稿中均是远程已上传素材。

发布与运营门槛

  • 来源展示策略在 Step 0 定义，而非临近发布时补救；
  • 若平台不适合外链，正文不临时塞“点击查看”承诺；
  • 草稿更新后回读校验标题、摘要、封面、图片和正文；
  • 没有显式发布指令时，停在草稿，不将“继续”解释为群发。
对现有 quality 命令的修正建议：保留它做“机械预警”（套话、句式、段落、重复），但删除或弱化任何“AI 味 25%”的结论性承诺。把编辑质量报告分为 自动检查 与 编辑判定 两栏，后者必须附具体证据和修改位置。

素材优先级与角色矩阵

素材级别优先级适用标注规则禁止的用法
第一方原始素材P0官方 demo、GIF、视频、截图、benchmark 图来源 official；保留原始标题/语义裁剪后改写成未出现过的官方结论
一手技术材料P1文档、论文、GitHub、产品演示来源 primary把描述性材料包装为独立评测
可信第三方P2独立 benchmark、媒体、客户公开材料来源 third_party + 时间忽略方法/样本限制
编辑解释图P3结构、流程、对比、读法来源 editorial + 生成/绘制说明充当官方案例截图或凭空制造“实测结果”
纯装饰生成图P4仅在品牌氛围确有必要时来源 decorative替代证据素材；重复担当封面、Hero、案例三种角色

Cover

完成点击前的识别与情绪。它可以是品牌化视觉，但不承担论证。

Hero（可选）

读者进正文后看到的第一份“证据/场景”。若只是重复 Cover，宁可删掉。

Evidence visual

证明一个具体事实、案例或数据。优先使用官方、原始或可溯源素材。

公开仓库的硬约束

必须进入设计，而不是靠“提交前小心”

  • 所有 provider key、AppSecret、cookie、浏览器 profile、Access Token 只允许存在于用户目录或本地 .env；README 只写变量名和占位值。

  • 示例文章使用匿名/虚构标识，不包含真实 draft ID、账号 ID、访问 URL 参数、客户未公开素材。
  • 加入提交前与 CI 的 secret scan；扫描失败时阻断提交，而不是只给提示。
  • 新增 SECURITY.md：漏洞报告通道、泄露凭据处理方式、明确不接受 issue 中粘贴密钥。

本次计划的安全状态

  • 本方案不包含任何真实 API key、账号凭据、草稿 ID 或会话数据。
  • 本方案不会自动修改运行配置、安装脚本、远程仓库或发布状态。
  • 后续实施时不应把本次文章运行目录复制到项目仓库。

验收标准：不要再靠“感觉已经好了”

流程级验收案例

  1. 用户说“写一篇刚发布模型的公众号文章”：系统先输出渠道契约、证据计划和素材策略；不直接生图。
  2. 用户要求“官方案例 + GIF”：系统优先检索一方素材，manifest 中区分 official 与 editorial。
  3. 用户选择“正文不要外链”：HTML audit 保证 <a>、href、可见 URL 均为 0，GIF 仍保留。
  4. 用户说“继续”：系统仅做下一个未完成产物；只有显式 PUBLISH 触发公开发布。

文章级验收 rubric

  1. 读完第一屏能说出：发布了什么、真正的变化是什么、本文要帮助谁判断什么。
  2. 每张正文图片有角色说明，且没有与封面/其他图重复承担角色。
  3. 每个核心结论有主张 ID 与证据等级，编辑推断有清晰限定。
  4. 编辑审校能指出至少一条原创取舍、一条反例/限制和一处删减理由。

执行选项与推荐

A · 最小修复

修 Skill 路由与文档漂移

修复失效引用；补 Baoyu 预检；更新 README；新增公开仓库 hygiene 规则。

C · 完整产品化

多平台内容操作系统

加入模板库、素材仓、A/B 标题、发布排程、回收数据和学习闭环。

适合：高频内容生产。

我的建议：选 B。 A 只能让“下次更不容易忘记 Baoyu”；B 才能解决更根本的“为什么资料、素材、写法和发布在最后才互相打架”。C 现在不划算。

若批准 B，实施顺序应为

  1. 先修引用与 README/Skill 一致性，并加入公共仓库防泄露基线；
  2. 再落地 channel contract、claims / sources / asset manifest、storyboard 模板；
  3. 把 Baoyu 改为早期 preflight、后期 production 的两段式路由；
  4. 补 run-level audit 与测试 fixtures；
  5. 用一次新的“模型发布公众号文章”完整走测，不直接拿本次已完成文章倒灌为成功样例。
明确不做：不自动公开发布；不默认生成一堆装饰图；不把没有的实测写成个人体验；不把任何本地凭据、运行文件或公众号草稿状态提交进公开仓库。
