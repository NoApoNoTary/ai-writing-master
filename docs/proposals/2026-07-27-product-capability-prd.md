# Product Capability MVP PRD

- 状态：Approved for P0 execution
- 日期：2026-07-27
- 负责方向：用户可见的产品能力与写作工作流体验
- 配套技术文档：[Handoff Runtime MVP PRD](2026-07-27-handoff-runtime-prd.md)

## Executive Decision

AI Writing Master 当前已经有较完整的写作方法、模式、角色和产物合同，但主要能力仍通过 Skill 文本表达。下一阶段的产品工作不是继续增加 Agent、平台和检查项，而是把现有能力收敛为一条用户能够开始、确认、继续、完成和验收的写作主链。

产品 P0 以标准写作为主路径。快速模式是缩短版，深度模式是增强版，三种模式共享同一套用户旅程和交付结构。Handoff Runtime 是深度模式的技术能力，不取代产品主链。

## Product Codex Execution Contract

本节供负责产品方向的 Codex 会话直接读取并执行。

### Role

你是 Product Capability Owner。你的工作是定义并落实用户可见行为、Skill 合同、功能状态、错误反馈和验收场景，不负责实现 Python 运行时与多 Agent 底层编排。

### Required Read Order

1. 本 PRD。
2. Writing Master 主 Skill。
3. 模式选择、证据与素材、Baoyu、审校参考文件。
4. Rewrite Skill 与平台合同。
5. [Handoff Runtime MVP PRD](2026-07-27-handoff-runtime-prd.md)，只理解技术边界。
6. 当前用户文档和产品合同测试。

仓库存在 `.codegraph/` 时，定位代码或测试前先使用 `codegraph explore`。

### Write Scope

产品 Worktree 可以修改：

- Writing Master 主 Skill；
- 除多 Agent 技术协议之外的产品参考文件；
- Rewrite Skill 与平台功能合同；
- 快速开始和用户操作文档；
- 产品合同与文档测试；
- 本 PRD 的实施状态和验收记录。

### Read-only Scope

- Python CLI 与运行时实现；
- Handoff Runtime PRD；
- 多 Agent Host Adapter 实现；
- 安装与构建配置。

当产品验收依赖尚不存在的运行时能力时，在本 PRD 的 Product–Technical Gap 中记录，不跨界编写临时实现。

### Forbidden Scope

- 不增加 Web UI、云服务、团队系统或通用 Agent 平台；
- 不扩大到新的内容平台；
- 不修改用户已有的未跟踪提案文件；
- 不把尚未实现的行为写成已经可用；
- 不以“更多 Agent”替代产品价值。

### Execution Order

1. 对照 P0 场景审计现有 Skill。
2. 只补阻断完整主链的产品合同与用户反馈。
3. 增加最少的合同测试。
4. 运行全部测试和 Markdown 链接检查。
5. 输出 P0 已完成项、Product–Technical Gap 和未开始的 P1–P3。
6. 只提交本 Worktree 拥有的文件。

### Stop Conditions

出现以下情况时停止扩大实现，并在结果中说明事实：

- 产品需求需要修改 Python 状态机或 Handoff Runtime；
- 当前 Skill 与技术 PRD 对同一状态定义冲突；
- 需要用户决定新的模式、平台或发布行为；
- 实现将迫使快速、标准模式启用多 Agent；
- 变更开始涉及商业模式、团队协作或托管服务。

### Done Criteria

- 标准写作从开始到交付具有完整用户旅程；
- 每个等待用户的节点都有明确问题和继续方式；
- 每个阶段都有用户可理解的状态与产物；
- 快速、标准、深度共享同一产品模型；
- 文档不宣称未实现的运行时能力；
- 产品合同测试通过；
- 未跨越技术 Worktree 的文件边界。

## Problem Statement

用户当前可以通过自然语言触发写作流程，但仍面临以下产品问题：

1. 模式选择之后，用户缺少统一的任务视图，不清楚当前阶段和下一步。
2. 用户提供的链接、视频、文件和图片缺少一个明确的素材接收结果。
3. Brief、方向确认、审校和发布确认分散在流程说明中，用户等待状态不统一。
4. `draft-v1`、`draft-v2` 和 `final` 已有文件合同，但版本之间的用户操作尚未产品化。
5. “继续上次”有文字说明，但用户不知道恢复了哪个任务、哪些输入已经变化。
6. 深度模式定义了角色分工，但用户真正需要看到的是进度、结果和阻断问题。
7. 最终交付仍容易退化成单篇正文，没有稳定的来源、素材、审校和验收包。
8. Rewrite、视觉和发布已经存在路由，但与 canonical final 的产品关系不够明确。

## Product Principle

产品能力围绕一个经济且可验证的单位组织：

> 一次能够从输入恢复、经过确认和审校、最终形成完整交付包的内容任务。

产品不以 Agent 数量、生成次数和 Token 消耗作为成功标准。

## Product Capability Map

```text
任务入口
  → 模式选择
  → 素材摄入
  → 内容契约
  → 调研与方向
  → 草稿与版本
  → 审校问题处理
  → 交付包
  → Rewrite / 视觉 / 排版 / 发布
  → 本地资产复用
```

## Primary User Journey

### 1. 创建任务

用户提出新建完整文章请求。

系统行为：

- 用户未明确模式时，只展示一次模式选择；
- 用户已明确模式时直接进入下一步；
- 模式未选择前不创建任务、不读取素材、不生成正文。

### 2. 接收素材

用户可以提供：

- URL；
- YouTube 链接或字幕；
- 本地 Markdown、文本或文档；
- 图片、GIF、视频和图表；
- 历史文章或个人素材。

系统返回一个简洁素材接收结果：

```text
已接收：3 项
已提取：2 项
等待处理：1 项
失败：0 项
需要你确认：素材 A 是否允许作为公开引用
```

用户不需要理解具体 Skill 路由。

### 3. 确认内容契约

系统整理并让用户确认：

- 主题；
- 目标读者；
- 发布平台；
- 内容目的；
- 篇幅；
- 时效要求；
- 证据等级；
- 视觉、排版和发布意图。

用户可以确认、修改或取消。没有必要逐字段追问已经能够从请求中确定的信息。

### 4. 查看任务状态

用户始终能够获得：

- 当前任务；
- 当前模式；
- 当前阶段；
- 已完成产物；
- 正在执行的动作；
- 等待用户的决定；
- 最近失败和继续方式。

产品层使用用户语言，不直接展示内部 schema 和 hash。

### 5. 确认写作方向

- Quick：默认给出一个建议方向；没有重大分叉时直接继续。
- Standard：给出 2–3 个具有真实取舍的方向。
- Deep：展示独立策划形成的候选方向，但不暴露父对话和内部推理。

用户确认后，核心方向成为后续正文和标题的约束。

### 6. 草稿与审校

用户可见状态：

```text
初稿完成
→ 审校发现 2 个阻断问题、3 个主要问题
→ 等待用户处理 1 个方向性问题
→ 修订完成
```

用户可以：

- 接受建议；
- 忽略非阻断问题；
- 修改原始要求；
- 要求重新生成受影响部分；
- 查看修订前后差异。

阻断事实问题不能通过“忽略”直接进入发布状态。

### 7. 完成交付

任务只有在以下产物满足本次请求时才标记完成：

- `final.md`；
- 来源与主张记录；
- 素材清单；
- 审校或修订报告；
- 验收报告；
- 用户要求时的视觉、HTML 或平台草稿。

用户收到简洁交付摘要和全部文件位置。

### 8. 后续动作

完成后用户可以独立选择：

- 按目标平台 Rewrite；
- 生成视觉和排版；
- 发布；
- 保存为个人素材；
- 复制任务作为新任务起点。

这些动作不改变 canonical final。

## User-visible State Model

内部阶段继续复用现有工作流，用户层统一为以下状态：

| 用户状态 | 含义 | 允许动作 |
|---|---|---|
| 等待模式 | 尚未选择快速、标准或深度 | 选择、取消 |
| 接收素材 | 正在登记和提取输入 | 继续添加、结束摄入、取消 |
| 等待契约确认 | Brief 已整理 | 确认、修改、取消 |
| 调研中 | 正在处理证据和素材 | 查看进度、补充素材、取消 |
| 等待方向确认 | 候选方向已形成 | 选择、修改、取消 |
| 写作中 | 正在生成或修订正文 | 查看阶段、取消 |
| 等待问题处理 | 存在需要用户决定的问题 | 接受、忽略非阻断项、修改要求 |
| 打包中 | 正在形成交付包 | 查看进度 |
| 已完成 | 核心交付包有效 | Rewrite、视觉、发布、复制任务 |
| 失败 | 当前动作未完成 | 查看原因、重试、回退、取消 |
| 已取消 | 任务停止但保留已完成产物 | 查看、复制、归档 |

## Functional Priorities

## P0：标准写作闭环

P0 是当前产品 MVP，优先于新增平台和高级 Agent 功能。

### P0.1 任务生命周期

- 新建任务；
- 查看当前任务；
- 继续指定任务；
- 取消任务；
- 完成后保持只读交付记录。

### P0.2 素材接收结果

- 列出已接收、已提取、失败和待确认素材；
- 失败项不阻塞无关素材；
- 真实素材与编辑生成素材身份分离；
- 用户可以结束素材摄入并继续。

### P0.3 内容契约确认

- 合并用户已经给出的信息；
- 只追问阻断字段；
- 输出单一确认摘要；
- 修改契约时标记受影响阶段。

### P0.4 进度与等待状态

- 每个阶段都有当前动作和下一步；
- 只在需要用户决定时中断；
- 失败原因包含可执行的重试入口；
- 恢复能力由技术 Worktree 提供，产品 Worktree定义用户表现。

### P0.5 草稿、审校与修订

- 保留初稿和最终稿；
- 审校问题具有位置、严重级别、证据和要求；
- 方向性问题集中询问用户；
- 修订报告逐项对应接受的问题。

### P0.6 统一交付包

- 明确定义任务完成所需的最小文件；
- 根据请求增加视觉、HTML 或平台草稿；
- 未请求发布时停留在草稿或验收状态；
- 用户能够查看交付缺失项。

## P1：深度模式产品化

- 独立角色真实执行；
- 显示当前角色、阶段、attempt 和阻断问题；
- 角色失败可以重试；
- 输入改变只重跑受影响节点；
- Auditor 问题先合并，再由 Writer 统一修订；
- 深度模式不增加无必要的用户确认次数。

技术实现由 Handoff Runtime PRD 负责。

## P2：内容复用与平台交付

- `final.md` 成为唯一 canonical source；
- 每个平台版本从 canonical source 独立生成；
- 记录平台版本与源稿版本关系；
- Baoyu 视觉和排版基于已稳定正文；
- 发布前始终要求明确确认；
- 平台失败不破坏 canonical final。

## P3：个性化与学习

只有 P0–P2 稳定后再推进：

- 个人素材库；
- 历史文章和风格档案；
- 用户接受和拒绝的问题；
- 人工最终修改记录；
- 可复用文章类型模板；
- 基于真实修改的本地规则更新。

在拥有足够真实修改记录前，不宣称自动学习用户风格。

## Functional Requirements

### FR-1 模式一致性

三种模式共享同一任务模型、用户状态和交付定义，只改变执行深度。

### FR-2 用户确认最小化

只有模式、内容契约、重大方向、阻断问题和发布需要强制确认。其他阶段默认连续执行。

### FR-3 产物优先

所有跨阶段结果写入任务目录；聊天只展示摘要、选择和文件位置。

### FR-4 失败可解释

失败结果必须说明：失败动作、影响范围、已保留产物和下一步。

### FR-5 Canonical Source

Rewrite、视觉、排版和发布只读取已经验收的 canonical final 及其关联产物。

### FR-6 能力发现

外部 Skill 不存在时，明确显示缺失能力和受影响功能，不把未执行结果描述为成功。

### FR-7 发布边界

准备发布和实际发布是两个状态。只有明确发布指令可以产生外部副作用。

## Acceptance Scenarios

### Scenario A：无素材标准写作

1. 用户请求新建文章。
2. 选择标准模式。
3. 确认内容契约。
4. 选择方向。
5. 收到初稿、审校结果、最终稿和交付摘要。
6. 未请求视觉和发布时，任务正常完成。

### Scenario B：带混合素材写作

1. 用户提供 URL、视频和本地图片。
2. 系统返回素材接收结果。
3. 一个素材失败时，其他素材继续处理。
4. 用户确认是否排除失败素材。
5. 最终交付包含来源与素材身份。

### Scenario C：中断恢复

1. 任务在等待方向确认时中断。
2. 用户指定 task_id 继续。
3. 系统展示恢复的任务、模式、阶段和待确认项。
4. 用户确认后从正确阶段继续，不重跑无关阶段。

### Scenario D：审校阻断

1. 审校发现事实来源不足。
2. 系统不进入已完成或发布状态。
3. 用户补充来源或降低表述强度。
4. 受影响部分重新审校后完成。

### Scenario E：Canonical Rewrite

1. 主任务完成 canonical final。
2. 用户请求小红书和抖音版本。
3. 两个版本独立生成。
4. 任一平台版本失败不修改 canonical final 和其他平台版本。

## Testing Decisions

- 优先测试用户可见行为和产物合同，不测试提示词措辞细节；
- 模式选择、等待状态、交付包和发布确认使用场景级合同测试；
- 运行时恢复和 Handoff 行为交给技术 Worktree 的端到端测试；
- 继续使用现有 `unittest`，不增加测试依赖；
- 每个新增产品分支至少有一个失败路径检查。

## Product–Technical Gap

以下产品能力需要技术 Worktree 承接：

| 产品能力 | 技术依赖 |
|---|---|
| 当前任务与 task_id | 确定性任务状态存储 |
| 继续上次 | 运行目录发现与状态恢复 |
| 输入变化后局部重跑 | 输入 hash 与依赖关系 |
| 深度模式角色状态 | Handoff Manifest、Result 和 Host Adapter |
| 失败重试 | attempt 历史和原子状态更新 |
| 版本回退 | 产物版本与不可变历史 |
| 发布记录 | 外部动作结果持久化 |

产品 Worktree 只定义用户行为，不为这些缺口编写伪运行时。

## Out of Scope

- 商业模式、定价和获客；
- Web UI；
- 团队协作；
- 云端同步；
- 通用 Agent 编排器；
- 新平台扩展；
- 自动发布所有平台；
- 没有真实修改数据的自动风格学习。

## Product Codex Final Return

完成工作后返回：

```text
status: pass | pass_with_changes | block
completed_p0:
product_behavior_changes:
tests_and_evidence:
product_technical_gaps:
```
