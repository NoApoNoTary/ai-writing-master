# AI Writing Master 产品 PRD：从流程工具到可信写作系统

- 版本：v1.0（初稿）
- 日期：2026-07-29
- 状态：待评审
- 依据：仓库 `codex/writing-workflow-maintenance` 分支产品评审（README、`docs/quick-start.md`、两个 SKILL.md、CLI 能力）
- 配套文档：`docs/2026-07-29-architecture-review.md`

> 标注约定：**[已验证]** = 评审中对照代码/文档确认的事实；**[假设]** = 需要用户研究或数据验证的判断；**[决策]** = 需要 owner 拍板的开放问题。

## 1. 产品定位

### 1.1 一句话定位

面向对事实准确性有职业要求的长文写作者，提供"每个关键事实可追溯、每次修改可验收"的 AI 写作流程，而不是一次性正文生成器。

### 1.2 目标用户

**[假设]** 核心画像：经常用 AI 写长文、且发布内容带事实责任的写作者——技术博主、newsletter 作者、行业分析师、独立开发者。

滩头市场：已在 Claude Code / Cursor / Codex 等 AI 编程工具中写作的人群（当前 Skill 形态的自然可达用户）。

**[决策]** 需要明确：agent-skills 形态是滩头策略还是终局形态？这决定后续所有渠道与分发投入。当前文档未回答此问题。

### 1.3 竞品心智

真正的竞品不是 Jasper/秘塔等 AI 写作工具，而是"直接让 ChatGPT/Claude 写"的零摩擦默认行为。用户迁移的唯一理由是**产出可信度**。因此产品护城河 = 证据链的用户可见性，而非流程复杂度。

### 1.4 差异化资产（[已验证]，评审确认已在仓库中实现）

- 证据双轨：`sources.yaml` + `claims.yaml`，关键事实带 `claim_id` 与来源；
- 不可变 Voice 快照：任务级冻结 + SHA-256，历史任务不受配置变更污染；
- Rewrite 源稿复用：同一 `source_sha256` 跨渠道复用 `source-analysis.md`，解决多渠道分发"重复解释背景"的核心痛点；
- 确认式风格学习（`learn`）：风格规则只在用户显式接受后进入后续任务；
- 停止型失败协议（WM-CAP-001/WM-RUN-001）：不降级、不伪装多 Agent，保信任。

## 2. 问题陈述（按用户价值排序）

### P1：核心承诺"可继续"在默认模式下不成立 —— 严重

**[已验证]** README 第一行承诺"可审阅、**可继续**、可验收"，但 `quick/standard`（含默认推荐的 standard）没有跨会话恢复（README:298 自述）。用户用推荐模式写到一半关闭对话 = 一切归零。

影响：品牌承诺违约风险；每次发生即流失一次信任。

### P2：停止型失败是死胡同 —— 严重

**[已验证]** WM-CAP-001 触发后任务直接结束，只提示"提交 Issue"（`skills/writing-master/SKILL.md:63`），且明确"不询问用户是否改用其他模式"。用户的写作需求没有任何出口。

该约束保护的是工程纯洁性，牺牲的是用户目标达成。不自动降级是对的，但"把选择权交回用户"与"自动降级"是两回事。

### P3：证据链对用户不可见 —— 高

**[已验证]** `sources.yaml`/`claims.yaml` 是机器格式；用户验收时看到的 `acceptance-report.md` 未把"关键事实 → 来源"映射作为一等公民呈现。**[假设]** 用户能感知"这个工具不一样"的唯一时刻就是点开事实看来源的时刻，当前这个时刻不存在。

### P4：重复使用的摩擦未设计 —— 高

**[已验证]** 每次新建文章必经模式选择闸门（SKILL.md:49-54），无默认项机制。首次使用建立预期是好的；**[假设]** 第 N 次使用时成为仪式性摩擦。注意：默认值可由**用户历史选择**产生，不违背"Agent 不代选"原则。

### P5：Voice 学习闭环无主动触达 —— 中

**[已验证]** `learn` 命令存在，但验收完成后系统不主动提示可学习的风格候选。**[假设]** "越用越像你"是最强留存引擎，被动等用户发现等于没有。

### P6：渠道覆盖与目标用户不匹配 —— 中

**[已验证]** 仅 wechat / x-post / x-thread。**[假设]** 中文目标用户首发渠道高度集中于知乎、少数派、Newsletter，缺席会压低中文用户首秀体验。

### P7：无可观测性 —— 中

**[已验证]** 无遥测（隐私优先，合理），但也无本地任务完成率/卡点统计。产品决策（闸门是否太烦、WM-CAP 触发率）目前完全无数据支撑。

## 3. 需求与方案

### P0-1：quick/standard 任务恢复（解决 P1）

- 用户故事：作为 standard 模式用户，我在写作中断后重新打开对话，说"继续"即可从上次阶段续跑，不重做已完成调研。
- 方案要点：恢复语义与执行模式正交——基于已有运行目录 + `status.json` 阶段合同定义各阶段可重入性、输入变化失效规则、产物续接点。复用现有锚定/锁/原子写基础设施（架构评审 §3.3）。
- 验收标准：standard 任务在任意阶段中断后可续跑；输入变化时只重做受影响阶段；恢复不依赖对话记忆。
- **这是下一版本的唯一 P0。**

### P0-2：失败出口岔路（解决 P2）

- 用户故事：模式未就绪时，我看到三个明确选项：① 改用可用模式继续（明示损失，如"损失研究/审计隔离"）；② 保留任务待环境就绪；③ 取消。
- 约束：不自动降级；选择必须由用户显式做出；诊断信息保留。
- 验收标准：WM-CAP-001 触发后用户任务达成路径存在；降级选择留痕于运行目录。

### P1-1：验收报告的证据链视图（解决 P3）

- 用户故事：验收时我看到一张表格：每条关键事实 | 来源 | 置信边界，可逐条追溯。
- 方案要点：`acceptance-report.md` 模板增加"事实-来源映射"章节，数据从 `claims.yaml`/`sources.yaml` 机械生成，零额外调研成本。
- 验收标准：每条 `claim_id` 在验收报告中可追溯；**[假设]** 这是 demo 与传播素材的核心展示面。

### P1-2：模式默认值学习（解决 P4）

- 用户故事：连续 3 次选 standard 后，闸门变为"本次默认标准写作，回复'换'可改"，可一键跳过。
- 约束：默认值仅来自用户本人历史选择计数，Agent 不得根据题目难度推断；用户可随时重置。
- **[决策]** 阈值（3 次？）与是否可配置需拍板。

### P1-3：风格候选主动提示（解决 P5）

- 用户故事：验收完成后，系统提示"本次有 2 条可学习的风格候选，要看看吗"，我确认后才进入 Style Profile。
- 约束：保持 accepted-only 语义不变，仅增加触达。

### P2-1：渠道扩展（解决 P6）

- 按"目标用户首发渠道"排序：**[假设]** 知乎 → Newsletter（通用 Markdown/email）→ 少数派/小红书。
- **[决策]** 下一个渠道的选取需要一轮目标用户访谈（5-8 人）确认，而非按实现成本排。

### P2-2：本地使用统计（解决 P7）

- 方案要点：CLI 增加本地聚合命令（如 `writing-master stats`），只读各运行目录 `status.json` 终态：任务完成率、各闸门停留分布、WM-CAP/RUN 触发次数。零遥测、零外发。
- 验收标准：维护者能回答"用户卡在哪个闸门"这类问题。

## 4. 增长与传播

- **Demo 资产（最高优先级）**：一份脱敏真实任务的完整运行目录 + 录屏，30 秒展示"带证据链的文章"。配套 P1-1 的验收报告视图作为传播素材。
- **可分享对比素材**：同一段文字 × 四个内置 Voice 的对比输出，是社交媒体上展示 Voice 能力的最低成本素材。
- **[假设]** 当前无"wow moment"快速通路：新用户从安装到第一篇成品需十余轮交互。可考虑 quick 模式的官方演示样例（用户提供主题，5 分钟内出稿）降低首秀门槛。

## 5. 非目标（本版本明确不做）

- 自动发布到任何平台（仓库现状已明确，保持）；
- 深度/多 Agent 改写（README 已标为 P0 之外，保持）；
- X Article、渠道数据反馈闭环（CHANGELOG 自述留后续阶段）；
- 遥测与云端同步（与隐私优先定位冲突）；
- 通用任务管理器（README:72 明确否定，保持）。

| 指标 | 基线 | 目标 | 测量方式 |

| 发起→验收完成率 | 未知（P7 解决后可测） | 首版测量，不设目标 | 本地 stats（P2-2） |
