# 这篇 GitHub 文章提醒我：AI 编程先别急着加工具

AI 编程工具越装越多，效率却未必跟着走。

最近看这类内容，很容易掉进一个误区：差距好像只在于你还没装某个 MCP、某个 Skill，或者少了一个“神奇提示词”。

但我刚看到的一篇 GitHub Blog 文章，专门把这个方向拧了回来。

2026 年 7 月 27 日，Burke Holland 在 GitHub Blog 发布《The harness is all you need (mostly)》。文章一开始就提到，AI 工具、模型、工作流和社交媒体技巧正在制造信息过载；作者的判断是：**真正影响效率的，往往不是又安装了什么，而是是否真正理解并掌握手上的 agent harness。** citeturn0view0

原文里有两句很适合当入口：**“less is way more”**，以及 **“The harness is all you need—mostly.”** citeturn0view0

我的结论先放在这里：**这篇文章适合写成公众号文章，也值得转给一部分开发者；但它适合做“发现型解读”，不适合照搬成一篇 Copilot 功能教程。**

## 原文说的，不是“一句提示词写完代码”

作者用日期选择器演示了一条很朴素的闭环：

```text
选定一个工具
→ 先做原型
→ 进入计划模式
→ 让代理执行计划
→ 人工检查并迭代
→ 用另一个模型做第二意见
→ 提交，或开启下一轮工作
```

这里的重点不在某个命令，而在顺序。

作者没有一上来让模型“直接写出最终版本”。他先让模型生成多个日期选择器方案，再从方案里发现原本没有说清楚的交互：年份、月份和日期怎么缩放，选中范围怎么显示，“Today”按钮该跳到哪一层。原文也把这套思路放到 API 设计里：先画出几种方案，再决定实现路径。citeturn0view0

这很像把模糊需求先摊到桌面上。东西一旦看得见，没做的决定也就藏不住了。

随后，计划模式继续追问边界条件，再交给 Autopilot 执行。初版出来后，作者逐条指出动画、对比度、导航和视觉层级的问题，再请求 Rubber Duck 用不同模型做一次复核。citeturn0view0turn1view1turn1view2

所以，这不是“一个提示词生成全部代码”的故事。

它在演示另一件事：**把模糊任务拆成可观察、可讨论、可检查的中间产物。**

## 真正有用的三件事

### 原型先出来，决定才看得见

AI 很适合介入的时机，常常不是需求已经写得非常完整之后，而是它还存在多个合理方向的时候。

低成本原型能把抽象争论变成具体对象。看过几个界面变体，你才可能发现，自己真正要的不是“一个日期选择器”，而是“允许用户在年、月、日之间来回缩放的日期导航”。

这不只适用于界面。API 的返回格式、权限策略、错误处理和异步流程，也都可以先用草图、流程图或几种候选方案摆出来。

**原型不替你拍板。它让你更早看见自己还没拍板的地方。**

### 计划模式负责找漏项，人负责做取舍

文章列出的问题很普通：起止日期能不能相同？是否允许部分选择？能否清空？日期该保存成什么格式？

也正因为普通，它们最常被漏掉。

很多人把“计划”理解成让模型吐出一份看起来很完整的 TODO。原文更有价值的地方是，计划模式应该继续提问，而人要参与回答、追问和纠正。

可以把这件事拆开看：

- 把**遗漏的边界问题**交给模型发现；
- 把**业务取舍和质量标准**留在人手里；
- 把“我以为我说清楚了”变成一份能检查的约束。

如果只是接受模型替你做的每一个决定，计划模式就只剩一份好看的清单。

### 第一版是材料，不是结果

作者很坦率地展示了初版日期选择器的问题：动画不一致、悬浮文字对比度不足、按钮行为不符合预期，甚至整体看起来“很像 AI 做的”。

这比“模型一键生成漂亮页面”有用得多。它提醒我们，第一版输出只是材料。

Rubber Duck 的思路也值得迁移：让不同模型对同一份计划、代码或测试给第二意见。GitHub Docs 对它的定义是一个只做批评和反馈的内置代理，使用与主会话不同的模型寻找盲点，并不直接修改文件。citeturn1view2

第二个模型不一定更正确。

但它能把单一模型的盲点，变成更容易被看见的一轮审查。

## 这三条边界也别省掉

### harness 不是 Copilot 的同义词

作者明确说，为了让文章更简单，他把 “harness” 和 GitHub Copilot 交替使用。这个定义对示范很方便，但不该被当成行业统一定义。citeturn0view0

如果把概念拆开，我更愿意把 harness 看成一组协作条件：

```text
模型 + 上下文 + 工具 + 权限 + 执行循环 + 反馈/验收
```

Copilot 是一种产品化实现。别的 AI 编程工具也可以有自己的 harness。

真正能迁移的，是这套结构，不是某个斜杠命令。

### YOLO / Allow All 是权限开关，不是效率按钮

原文把 “Allow All” 放进工作流第二步，这里很容易被中文读者误读。

GitHub Docs 说明，`--allow-all`、`--yolo` 或 `/allow-all` 会把所有可用工具、路径和 URL 的权限交给 CLI；官方同时强烈建议只在隔离环境中使用。citeturn1view0turn1view1

所以更准确的说法是：**代理需要足够的行动空间，才能少一些重复确认；但权限扩大必须和环境隔离、数据边界、可回滚性一起设计。**

GitHub Codespaces 的确提供云端开发环境，把代码运行在虚拟机上的 Docker 容器中。它可以是一层隔离，但容器本身不等于完整的安全和成本治理方案。citeturn1view3

如果只写“打开 YOLO，效率起飞”，最重要的边界就被删掉了。

### Autopilot 和异模型复核都要算成本

Autopilot 的好处是，它能在初始指令之后连续执行多步；但官方文档也明确说，它更适合边界清楚、步骤明确的任务，不适合目标含糊的开放式探索。它会持续消耗模型额度；在授予相应权限时，也可能修改或删除文件。citeturn1view1

Rubber Duck 也不是免费的质量保证。它会增加一次额外推理，当前文档还注明，只有当主代理使用 Claude 或 GPT 大模型时才可用。citeturn1view2

所以，成熟做法不是“所有任务都自动化”。

先检查目标是否足够明确、中间产物能否检查、失败后是否可回滚，以及多一次模型调用是否值得换来更少返工。

## 换成别的 AI 工具，也该保留这五层

| 层次 | 要固定的东西 | 常见失败信号 |
| --- | --- | --- |
| 模型 | 一个任务期间尽量保持稳定 | 频繁换模型，上下文和判断标准不断漂移 |
| 上下文 | 一个功能或问题对应一个主题会话 | 需求、修复、闲聊混在一起 |
| 工具 | 只开放当前任务需要的工具 | 工具越多，错误路径越多 |
| 执行 | 先原型、再计划、后实施 | 一上来就让模型改完整个仓库 |
| 反馈 | 人工验收、测试、第二意见 | 看到“能运行”就停止 |

这也是我觉得文章值得转发的原因。

它给出的不是一套只能在 Copilot 里使用的命令，而是一种能迁移的任务组织方式。

## 做一个一周实验，先别装新东西

如果想验证这篇文章对自己有没有用，做一个风险可控的小实验就够了：

1. 选一个重复出现、但风险可控的任务，例如补测试、做一个小组件或整理一个接口。
2. 固定一个模型和一个工具，不新增 MCP、Skill 或自定义 Agent。
3. 先要求模型给出多个原型或方案，不急着写最终代码。
4. 让模型列出边界问题，自己逐条确认。
5. 在隔离目录或容器中执行，保留人工检查环节。
6. 随后让第二个模型只做审查，不直接改文件。
7. 记录三件事：返工次数、遗漏的问题、总耗时。

如果没有改善，也别急着继续堆工具。

瓶颈可能在上下文、需求、权限、模型能力，或者验收标准。先把它找出来。

## 它适合谁？

**适合：**

- 已经装了很多工具，却仍然频繁返工的人；
- 想建立团队 AI 编程流程，但还没有找到最小闭环的人；
- 刚开始使用 Agent，希望先学会基本工作方式的人。

**不适合：**

- 只想找一份最新 Copilot 命令清单的人；
- 需要生产率对照实验、成本数据或团队规模化证据的人；
- 不做软件任务，只想看模型炫技的人。

原文是一个很好的实践示范，但没有提供严格的生产率实验，也没有证明这条流程对所有项目都成立。

把它写成“作者的经验 + 我们的抽象 + 官方文档的边界”，会比写成“Copilot 的八步神功”更诚实，也更有用。

## 收束

这篇文章最值得保留的，不是 “harness 是全部答案”这句标题，而是标题里的括号：**mostly**。

先用最简单的工具和流程，做出可重复、可检查的结果。只有明确知道瓶颈在哪里，再去增加 MCP、Skill、Custom Agent 或更复杂的编排。

复杂度应该由真实的失败证据换来，不该由焦虑驱动。
