# 我为什么把这篇 GitHub 文章转给你：AI 编程先别急着加工具

最近看 AI 编程内容，很容易产生一种错觉：效率的差距，来自你还没有装上某个 MCP、某个 Skill，或者还没有掌握某个“神奇提示词”。

但我刚发现的一篇 GitHub Blog 文章，故意把方向拧了回来。

2026 年 7 月 27 日，Burke Holland 在 GitHub Blog 发布了《The harness is all you need (mostly)》。文章开头就承认，AI 工具、模型、工作流和社交媒体技巧正在制造信息过载；作者给出的判断是：**真正影响效率的，往往不是你又安装了什么，而是你是否真正理解并掌握手上的 agent harness。** citeturn0view0

原文有两句很适合作为这篇文章的入口：**“less is way more”**，以及 **“The harness is all you need—mostly.”** citeturn0view0

我的结论先放在这里：**这篇文章适合写成公众号文章，也值得转给一部分开发者；但它适合做“发现型解读”，不适合照搬成一篇 Copilot 功能教程。**

## 原文到底讲了什么？

作者用一个日期选择器作为演示，把 AI 编程拆成一条很朴素的闭环：

```text
选定一个工具
→ 先做原型
→ 进入计划模式
→ 让代理执行计划
→ 人工检查并迭代
→ 用另一个模型做第二意见
→ 提交，或开启下一轮工作
```

这里最值得注意的，不是其中某个命令，而是顺序。

作者没有一上来要求模型“直接写出最终版本”，而是先让它生成多个日期选择器方案，再从这些方案中发现自己原本没有说清楚的交互：年份、月份和日期如何缩放，选中范围如何显示，“Today”按钮应该跳到哪一层等。原文还把同样的思路扩展到 API 设计：先让模型画出几种方案，再决定实现路径。citeturn0view0

随后，作者让计划模式继续追问边界条件，再交给 Autopilot 执行；看到初版结果后，作者逐条指出动画、对比度、导航和视觉层级问题，再请求 Rubber Duck 做一次不同模型的复核。citeturn0view0turn1view1turn1view2

这不是“一个提示词生成全部代码”的故事。它更像是在演示：**把模糊任务变成一组可观察、可讨论、可检查的中间产物。**

## 这篇文章真正有用的三点

### 1. 先做原型，不要先争论最终答案

AI 最适合介入的时机，常常不是需求已经写得非常完整之后，而是需求还存在多个合理方向的时候。

一个低成本原型可以把抽象争论变成具体对象。看到几个界面变体之后，你才会发现：自己真正想要的可能不是“一个日期选择器”，而是“允许用户在年、月、日之间来回缩放的日期导航”。

这对非视觉任务也成立。一个 API 的返回格式、权限策略、错误处理和异步流程，同样可以先用草图、流程图或几种候选方案呈现出来。

**原型的价值不是替你做决定，而是让你更早看到自己还没有做出的决定。**

### 2. 计划模式的价值，是暴露问题，不是替你拍板

文章列出的那些问题很普通：起止日期是否可以相同？是否允许部分选择？是否支持清空？日期保存成什么格式？

但正因为普通，它们才经常被遗漏。

很多人使用 AI 编程工具时，把“计划”理解成让模型输出一份看起来完整的 TODO 列表。原文更有价值的地方在于：计划模式应该持续向你提问，而你要参与回答、追问和纠正。

换句话说：

- 把**遗漏的边界问题**交给模型发现；
- 把**业务取舍和质量标准**留在人手里；
- 把“我以为我说清楚了”变成一份可以检查的约束。

如果你只是接受模型提出的每一个决定，计划模式就失去了意义。

### 3. 质量来自迭代和复核，不来自第一次生成

作者很坦率地展示了初版日期选择器的问题：动画不一致、悬浮文字对比度不足、按钮行为不符合预期，甚至整体看起来“很像 AI 做的”。

这段比“模型一键生成漂亮页面”更有用。它提醒我们，AI 输出的第一版只是材料，不是结果。

Rubber Duck 的思路也值得迁移：让不同模型对同一份计划、代码或测试给出第二意见。GitHub Docs 对它的定义是一个只做批评和反馈的内置代理，它使用与主会话不同的模型来寻找盲点，并不直接修改文件。citeturn1view2

这并不等于“第二个模型一定正确”。它只是把单一模型的盲点，变成了一个更容易被看见的审查环节。

## 但这篇文章有三处需要保留判断

### 第一，harness 不应该被简单等同于 Copilot

作者明确说，为了保持文章简单，他把 “harness” 和 GitHub Copilot 交替使用。这个定义对文章示范很方便，但不应被当成行业统一定义。citeturn0view0

如果把概念抽象出来，我更愿意把 harness 理解成一组协作条件：

```text
模型 + 上下文 + 工具 + 权限 + 执行循环 + 反馈/验收
```

Copilot 是其中一种产品化实现。其他 AI 编程工具也可以有自己的 harness。真正可迁移的是这套结构，而不是某个斜杠命令。

### 第二，YOLO / Allow All 是权限开关，不是效率按钮

原文把 “Allow All” 放在工作流第二步。这里最容易被中文读者误读。

GitHub Docs 说明，`--allow-all`、`--yolo` 或 `/allow-all` 会把所有可用工具、路径和 URL 的权限交给 CLI；官方同时强烈建议只在隔离环境中使用。citeturn1view0turn1view1

所以更准确的表述应该是：**代理需要足够的行动空间，才能减少重复确认；但权限扩大必须和环境隔离、数据边界、可回滚性一起设计。**

GitHub Codespaces 确实提供了云端开发环境，并将代码运行在虚拟机上的 Docker 容器中；它可以作为隔离层之一，但容器本身不等于完整的安全和成本治理方案。citeturn1view3

公众号文章如果只写“打开 YOLO，效率起飞”，那就把原文最重要的边界删掉了。

### 第三，Autopilot 和异模型复核都有成本和适用范围

Autopilot 的优点是可以在初始指令后连续执行多步；但官方文档也明确说，它更适合边界清晰、步骤明确的任务，不适合目标含糊的开放式探索。它还会持续消耗模型额度；在授予相应权限时，也可能修改或删除文件。citeturn1view1

Rubber Duck 也不是免费的质量保证。它会增加一次额外推理，当前文档还注明，只有当主代理使用 Claude 或 GPT 大模型时才可用。citeturn1view2

因此，真正成熟的做法不是“任何任务都自动化”，而是先判断：

- 目标是否已经足够明确？
- 中间产物是否可检查？
- 失败后能否回滚？
- 多一次模型调用，是否值得换取更少的返工？

## 把它迁移到其他 AI 工具，应该保留什么？

如果去掉 Copilot 的产品名，这篇文章可以压缩成五个层次：

| 层次 | 要固定的东西 | 常见失败信号 |
| --- | --- | --- |
| 模型 | 一个任务期间尽量保持稳定 | 频繁换模型，上下文和判断标准不断漂移 |
| 上下文 | 一个功能或问题对应一个主题会话 | 需求、修复、闲聊混在一起 |
| 工具 | 只开放当前任务需要的工具 | 工具越多，错误路径越多 |
| 执行 | 先原型、再计划、后实施 | 一上来就让模型改完整个仓库 |
| 反馈 | 人工验收、测试、第二意见 | 看到“能运行”就停止 |

这也是我认为文章最值得转发的原因：它提供的不是一套只能在 Copilot 里使用的命令，而是一种可以迁移的任务组织方式。

## 给你一个最小实践，不要先装新东西

如果你想验证这篇文章是否对自己有用，可以做一个为期一周的小实验：

1. 选一个重复出现、但风险可控的任务，例如补测试、做一个小组件或整理一个接口。
2. 固定一个模型和一个工具，不新增 MCP、Skill 或自定义 Agent。
3. 先要求模型给出多个原型或方案，不急着写最终代码。
4. 让模型列出边界问题，自己逐条确认。
5. 在隔离目录或容器中执行，保留人工检查环节。
6. 随后让第二个模型只做审查，不直接改文件。
7. 记录三件事：返工次数、遗漏的问题、总耗时。

如果结果没有改善，先不要继续堆工具。你需要先判断，瓶颈究竟在上下文、需求、权限、模型能力，还是验收标准。

## 这篇文章对谁有用？

**适合：**

- 已经装了很多工具，却仍然频繁返工的人；
- 想建立团队 AI 编程流程，但还没有找到最小闭环的人；
- 刚开始使用 Agent，希望先学会基本工作方式的人。

**不适合：**

- 只想找一份最新 Copilot 命令清单的人；
- 需要生产率对照实验、成本数据或团队规模化证据的人；
- 不做软件任务，只想看模型炫技的人。

原文是一个很好的实践示范，但它没有提供严格的生产率实验，也没有证明这条流程对所有项目都成立。把它写成“作者的经验 + 我们的抽象 + 官方文档的边界”，会比写成“Copilot 的八步神功”更诚实，也更有用。

## 收束

这篇文章最值得保留的，不是“harness 是全部答案”这句标题，而是标题里的括号：**mostly**。

先用最简单的工具和流程，做出可重复、可检查的结果；只有当你明确知道哪里出了瓶颈，再去增加 MCP、Skill、Custom Agent 或更复杂的编排。

复杂度应该由真实的失败证据换来，而不是由焦虑驱动。
